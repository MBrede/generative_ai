Embedding-based LLM-systems

All agents (and all LLM-pipelines if sufficiently complex) we discussed until here are using tools that allow them to use their generated inputs in some way. In most of the task we want to utilize LLMs, we do not only want to generate text but to also inform the generation based on some kind of existing knowledge base. Examples for these kinds of usecases include:

  • Answering questions about a specific topic (e.g., a company or product)
  • Summarizing a document
  • Generating a report based on data

Though most modern LLMs are increasingly capable in answering basic knowledge-questions, the more complex a topic or the more relevant the factual basis of an answer is, the more it is important to base generated answers on actual data.

Semantic embeddings and vector stores

To empower a LLM too look up information during its thought-process, one has to build a tool that allows a LLM to use natural language to retrieve information necessary for a task. The fundamental principle to do this are so-called semantic embeddings. These are pretty close to the concept we introduced when talking about the foundations of LLMs (see here) and can be understood as a way to map textual data into a vector space. The main idea is that semantically similar texts should have similar embeddings, i.e., they are close in the vector space. Close in this context is meant as having a reasonably small distance between them. The go-to standard to measure this distance is the cosine similarity, which has proven useful enough to be the standard for a range of semantic retrieval implementations (i.e., they are used in OpenAI tutorials and in Azure AI Foundry embedding-applications). The cosine similarity is defined as:

\[ \text{cosine\_similarity}(u, v) = \frac{u \cdot v}{\|u\| \|v\|} = \frac{\sum_{i=1}^{n} u_i v_i}{\sqrt{\sum_{i=1}^{n} u_i^2} \sqrt{\sum_{i=1}^{n} v_i^2}} \] The rationale here is that sequences with semantically similar contents should point to similar directions in the high dimensional vector space. See Figure 6.1 for an illustration of this and other common similarity concepts seen in semantic retrieval.

As always, there is not the one solution to all problems though and the applicability of cosine similarity might not be optimal for your usecase (Goyal & Sharma, 2022; Steck et al., 2024).

Though one could use any kind of (L)LM to calculate embeddings for this case1, it is advisable to use models specifically trained for this purpose. Reimers & Gurevych (2019) proposed Sentence-BERT which is a simple but effective approach to calculate semantic embeddings. SBERT and similar approaches are based on a (L)LM that was trained to predict missing words as we discussed before, resulting in a general representation of natural language. In the case of the original paper, they used (among others) the BERT model Devlin et al. (2019) mentioned before.

1 And there are approaches to use LLMs to solve this taks i.e., Jiang et al. (2023)

2 The original BERT-paper did this by adding a pooling layer before the task-header that extracted and weighed the context-dependend embedding of the first token. The SBERT paper tried different pooling-strategies and used a mean over each embedding dimension of the sequence.

The authors then use this to embed a pair of sentences into one embedding-vector each2, for which some measure of semantic similarity is known. An example for a dataset containing such sentences is the Stanford Natural Language Inferenc(SNLI) corpus Bowman et al. (2015) which labels 550k pairs of sentences as either entailment, contradiction or neutral. Reimers & Gurevych (2019) then concated the both senteces embeddings and their element-wise difference into a single vector which is fed to a multiclass classifier, indicating in which category the sentences relationship falls. At inference, this classification head was removed and replaced as the cosine similarity as discussed above. The resulting network is highly effective in calculating semantic similarities between sentences.

A look at the sbert-website shows that the module has somewhat grown and now does supply a series of learning paradigms that can be used to efficiently tune a model for your specific usecase3. As the library has grown, so has the sheer amount of pretrained embedding-models in some way based on this architecture that are hosted on huggingface. The MTEB-Leaderboard is a good start to search for a model for your application. One utilization of this model-family, which has already been implicitly used in this script, is their very efficient ability to semantically search for documents. If a model is very good at finding similar sentences, it can also be very good to find documents that are very similar to a question.

3 And this does not have to be expensive. Tunstall et al. (2022) have shown a highly efficient contrastive learning paradigm that limits the amount of necessary labels for a ridiculously small amount of labels.

Look at the example illustrated in Figure 6.2. The question “why is the sky blue” embedded with the same model as our 5 documents stating some facts.

We can then calculate the cosine-similarity between these embeddings and return the document, that has the highest similarity to our question.

This approach of using a model to embed documents and questions into a vector space is the basis for the so-called Retrieval augmented generation.

Retrieval augmented generation

Retrieval augmented generation (RAG) is a framework that does pretty much do what it says on the tin. You use a retrieval model to find documents that are similar to your question and then either return these documents or feed them into a generative model, which then generates an answer based on these documents. This process can additionally be wrapped as a tool to be used by an agent, so that your existing agent can now also use external knowledge sources to answer questions.

Retrieval does not have to be semantics-based in this context - all kinds of data sources and databases can be made accessible for a LLM - we will focus on a purely embedding based approach here though.

Although the small example in the last task was working, it is not really scalable. It was fine for a limited set of examples, if you want to realistically make a whole knowledge base searchable, you need to use an appropriate database system.

Vector databases

A vector database is a database that stores vectors and allows for efficient similarity searches. As can be seen in the db-engines ranking there has been a surge of interest in this area recently, with many new players entering the market. From the plethora of vector databases, these three are examples that virtue a honorary mention:

  1. Chroma - a in-memory database for small applications that is especially easy to get to run.

  2. Elasticsearch - a well established database that is the go to system for open source search engines and has recently (and kind of naturally) also branched out into vector databases.

  3. Qdrant - the product of a Berlin-based startup that focusses on stability and scalability. It can also run in memory, but does natively support hard drive storage.

The best way to use qdrant is to use docker to run it and the python sdk to interact with it. Since version 1.1.1, the sdk also allows to just run the client in memory.

RAG

The last step to make this into a RAG pipeline is to use a generative model to answer the question based on the retrieved documents.

This means, that we do collect the relevant documents like we did before, still based on a natural language question, but instead of returning the hits we got from the index, we feed them into a LLM and ask it to generate an answer based on these documents. This is where the name retrieval augmented generation comes from - we use the retrieval step to augment the generative model with additional information. Most agent frameworks provide integrations for a variety of vector databases.

Others, like Google’s Agent Development Kit (ADK), skip the wrappers: the retrieval stays plain qdrant code, and the agent just gets it as a tool. See Tip 6.1 for an example RAG-system implemented with ADK.

Tip 6.1: ADK Rag

ADK does not ship its own vector-store wrappers. This is less of a drawback than it sounds: the retrieval part stays exactly the plain qdrant and sentence-transformers code from above, and ADK only enters the picture when an LLM is supposed to use it.

The first step is again the setup of a vector database and an embedding model:

def chunk(text: str, size: int = 100, overlap: int = 20) -> list[str]:
    words = text.split()
    return [" ".join(words[i:i + size]) for i in range(0, len(words), size - overlap)]

chunks = chunk(text)

client.upsert(

)

The retrieval itself is a plain Python function. In ADK, any function with type hints and a docstring can be handed to an agent as a tool; the docstring becomes the tool description the model sees.

def find_references(question: str) -> str:
    """Query a database containing the paper "Attention is all you Need" in parts.
    This paper introduced the mechanism of self-attention to the NLP-literature.
    Returns a collection of scored text-snippets that are relevant to your question."""
    hits = client.query_points(
        collection_name="paper",
        query=embedder.encode(question).tolist(),
        limit=5,
    ).points
    return "\n".join(f"{round(h.score, 2)} - {h.payload['text']}" for h in hits)

To use the tool, we need an agent. We use Google’s Agent Development Kit (ADK) here, which we will look at in more detail in the session on agents (uv add google-adk litellm). ADK talks to local models through a LiteLlm wrapper, whose model string starts with a provider prefix (ollama_chat/ for Ollama). The helper below keeps that string in one place, so swapping models is a one-word change:

import os
from google.adk.models.lite_llm import LiteLlm

os.environ["OLLAMA_API_BASE"] = "http://localhost:11434"

def model(name: str) -> LiteLlm:
    return LiteLlm(model=f"ollama_chat/{name}")

Since we are going to ask several agents several questions, we also wrap the Runner-boilerplate into a small function. It prints every tool call, so we can see whether the agent actually used the database, and it skips the model’s reasoning (“thinking”) parts, so only the answer is returned:

from google.adk.agents import LlmAgent
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types

def ask(agent: LlmAgent, question: str) -> str:
    session_service = InMemorySessionService()
    runner = Runner(agent=agent, app_name="rag", session_service=session_service)
    session = session_service.create_session_sync(app_name="rag", user_id="student")
    answer = ""
    for event in runner.run(
        user_id="student",
        session_id=session.id,
        new_message=types.Content(role="user", parts=[types.Part(text=question)]),
    ):
        for call in event.get_function_calls():  # a model may request several calls at once
            print(f"[tool call] {call.name}({call.args})")
        if event.is_final_response() and event.content:
            answer = "".join(p.text for p in event.content.parts if p.text and not p.thought)
    return answer

    name="paper_assistant",

    instruction="You answer questions about scientific papers.",
    tools=[find_references],
)

print(ask(agent, "What is the meaning of Query, Key and Value in the context of self-attention?"))
[tool call] find_references({'question': 'What is the meaning of Query, Key and Value in the context of self-attention?'})


In the context of self-attention, **Query**, **Key**, and **Value** are vector representations derived from the input sequence, each serving a specific role:

1. **Query (Q)**: Represents the **focus** of attention. It determines what parts of the sequence the model should attend to. The query is used to compute compatibility scores with keys.

2. **Key (K)**: Represents the **features** used to compute compatibility with queries. The key encodes information about each position in the sequence, allowing the model to measure how relevant a particular position is to the query.

3. **Value (V)**: Represents the **content** that is weighted based on the compatibility scores. The value is the actual information that is aggregated (via weighted sum) to form the output.

### How they work together:
- The **attention weights** are computed by comparing the query (Q) to all keys (K) using a dot-product (or other compatibility function), normalized by a scaling factor (e.g., √dk).
- These weights are then applied to the corresponding values (V) to produce a weighted sum, which becomes the output for that position.

### Example:
In self-attention, all queries, keys, and values come from the same sequence. For each position, the model computes attention weights to determine how much to focus on other positions, enabling it to capture dependencies across the sequence. 

This mechanism allows the model to dynamically prioritize relevant parts of the input when processing information.

The agent does call the tool, but have a close look at the answer: it reads like general knowledge about attention, and nothing in it points back to the retrieved passages. We cannot tell which parts come from the paper and which from the model’s training data. Nothing in the instruction told the model that the retrieved text should be the basis of its answer.

One way to steer the agent is to be more explicit in the system prompt. In ADK, the system prompt is simply the instruction of the agent:

strict_agent = LlmAgent(

    model=model("qwen3:4b"),
    instruction="""You are designed to help answer questions based on a collection of paper-excerpts.
You have access to tools that allow you to query paper-content.
Do not answer without tool-usage if a tool can be used to answer a question.
Always back up your claims with a text passage you retrieved and quote it.
If the tools do not return relevant passages, say so instead of guessing.""",
    tools=[find_references],
)

print(ask(strict_agent, "How does the paper 'Attention is all you need' define the term self attention?"))
[tool call] find_references({'question': "How does the paper 'Attention is all you need' define the term self attention?"})


The paper "Attention is all you need" defines **self-attention** as an "attention mechanism relating different positions of a single sequence in order to compute a representation of the sequence" (score: 0.58). It emphasizes that self-attention, also termed **intra-attention**, allows every position in a sequence to attend to all others, enabling the model to capture dependencies between arbitrary positions within the same sequence. This mechanism is critical for tasks like reading comprehension and summarization, as it allows the model to weigh the importance of different elements in the sequence dynamically. 

Key passage:  
*"Self-attention, sometimes called intra-attention is an attention mechanism relating different positions of a single sequence in order to compute a representation of the sequence."*  

This is elaborated further in section 3.2 of the paper.

Now the answer is short, quotes the retrieved definition and stays close to the source.

Whether an agent uses its tools reliably depends heavily on the model. Very small models (around 1 billion parameters) frequently skip the tool and answer from their own, possibly hallucinated, knowledge, or produce malformed tool calls. Try swapping in a smaller model in the model(...) calls above and compare. Using a bigger model is not always feasible though.

Another way to use the retrieval-pipeline is to not give a weak model the opportunity to mess up the tool calling at all. Instead of letting the model decide whether to retrieve, Python always retrieves and hands the snippets to the model, whose only job is to summarize them. This is the deterministic-routing pipeline idea we will meet again in the session on LLM pipelines: the control flow is fixed in code, the LLM fills in one well-defined step.

summarizer = LlmAgent(
    name="summarizer",
    model=model("qwen3:4b"),
    instruction="""Answer the question using only the provided text snippets.
Quote the snippets you use. If they do not contain the answer, say so.""",
)

def rag(question: str) -> str:
    snippets = find_references(question)
    return ask(summarizer, f"Question: {question}\n\nSnippets:\n{snippets}")

print(rag("What is the meaning of Query, Key and Value in the context of self-attention?"))
In the context of self-attention, **Query**, **Key**, and **Value** are components of an attention mechanism:  
- **Query** is a vector that determines what information to focus on.  
- **Key** is a vector used to compute compatibility with the Query, determining relevance.  
- **Value** is the information that is weighted and summed based on the compatibility between the Query and Key.  

The output is a weighted sum of the Values, where the weights are computed by a compatibility function (e.g., dot-product) between the Query and Keys. In self-attention, all Queries, Keys, and Values originate from the same sequence, enabling each position to attend to others in the sequence.  

**Snippets used**:

0.52: "Queries and keys of dimension dk... values of dimension dv... dot products of the query with all keys... softmax function to obtain the weights on the values."  
0.53: "Self-attention... relates different positions of a single sequence... all queries, keys, and values come from the same place."

Since the retrieval no longer depends on the model’s decision, this also works with models that are too small for reliable tool calling.

Document chunking

The examples we looked at until now were all working with short text-snippets that comforably fit into the context window of a LLM. If you think about usual usecases for RAG-systems, this is not the most common case though. Usually, you will have a base of documents that can span multiple 1000’s of tokens and you want to be able to answer questions about these documents. Furthermore, you do not only want to know which document might be relevant, but ideally also which part of the document matches your question best.

This is where the process of doctument chunking or document splitting comes into play. There is a series of possible approaches to split a document, the most common, so called naive chunking method, is to use a structural element of the document though. This means that you parse the documents into sentences, paragraphs or pages and then use these as chunks that you individually embed and store in your vector database. To prevent loss of relevant context when splitting a document into chunks, it is additionally common to add some overlap between the chunks. This tries to solve the lost context problem, does however create reduncencies in the data.

An alternative approach is to use semantic chunking. This means that you split a document into chunks based on their meaning. Jina.ai explained in a blogpost (Late Chunking in Long-Context Embedding Models, 2024) their so called “late chunking” method. which iteratively runs the whole document through the attention head of the transformer to gain embeddings per token, and then averages these embeddings per naive chunk. This way, the chunks are still structure based but contain semantic information about the whole context.

Another approach to semantic chunking is described on the doc-pages of LlamaIndex. In their approach to semantic chunking, an adaptive splitting-rule is used, that splits the documents based on semantic similarity of sentences. This means that sentences that are semantically similar are grouped together into chunks.

Query Expansion/Transformation

Until now, we have based our retrieval on the assumption, that the question the user formulates is a good representation of their information need. This is not always the case though. Often, users do not know what they are looking for or they use synonyms or paraphrases that are not present in the documents. If the question is not formulated well, or if it is too specific, the system might not be able to find relevant documents. To improve the quality of the questions, we can use query expansion. This means that we take the original question and expand it with additional information to make it more specific and to increase the chances of finding relevant documents. This can be done in multiple ways, one common approach is to use a generative model to generate multiple queries based on the original question. Another approach is to use a keyword extraction algorithm to extract keywords from the question and then use these keywords to expand the query.

The most basic way to implement a query-expansion is to build a tool that instructs a LLM to give multiple alternate formulations of the original query. Though this will probably work, there are more refined methods.

Two more sophisticated approaches to transform queries are:

  1. Hypothetical Document Embeddings (HyDe): A LLM is instructed to generate a hypothetical document that answers the query. This document is then used to query the index

  2. Multi-Step Query Transformations: After a first execution of a (complex) query against an index, the answer is used to iteratively formulate follow-up questions that are then executed against the index.

Hybrid Search

So far, we have focused exclusively on semantic search using vector embeddings. However, purely semantic approaches can sometimes miss documents that contain exact keyword matches or specific terminology that users explicitly mention in their queries. This is where hybrid search becomes valuable by combining multiple retrieval strategies.

Hybrid search integrates semantic search with traditional keyword-based methods (like BM25 or full-text search) to leverage the strengths of both approaches. Semantic search excels at understanding context and finding conceptually related documents, while keyword search ensures exact matches are not missed.

Qdrant supports hybrid search through its multi-stage query capabilities. The basic approach involves:

  1. Parallel retrieval: Execute both a dense vector search (semantic) and a sparse vector search (keyword-based) simultaneously
  2. Score fusion: Combine the results using a fusion strategy such as Reciprocal Rank Fusion (RRF) or weighted scoring
  3. Re-ranking: Optionally apply a re-ranking strategy to refine the final result ordering (e.g., using Maximal Marginal Relevance or a higher-resolution embedding-model like ColBERT Santhanam et al., 2022)

Qdrant’s implementation allows you to configure how these different search strategies are weighted and combined. For example, you might give more weight to semantic similarity for conceptual queries, while prioritizing keyword matches for queries containing specific technical terms or proper nouns.

RAG Evaluation

Building a RAG system is one thing, but understanding whether it actually works well is another challenge entirely. RAG evaluation is crucial for iteratively improving your system and understanding its limitations.

RAG evaluation can be approached from multiple angles:

Component-Level Testing

Individual components of your RAG pipeline can be tested separately:

  • Retrieval quality: Are the right documents being retrieved? Metrics include precision, recall, and Mean Reciprocal Rank (MRR)4
  • Generation quality: Does the LLM produce accurate, relevant, and coherent answers given the retrieved context?
  • End-to-end: Does the complete pipeline answer questions correctly?

4 A score that indicates how far down the list of results the first correct answer is.

Frameworks like DeepEval provide tools for automated RAG evaluation. DeepEval offers three central, LLM as a judge-based RAG-specific metrics:

  1. Contextual Precision: an indication whether relevant nodes are ranked higher than irrelevant ones.

  2. Contextual Recall: this metric indicates to what extent the retrieved nodes align with the expected output.

  3. Contextual Relevance: an evaluation in how far each returned note is at all relevant to the query.

Since the base for these scores is an assessment of a LLM, these scores can both be calculated for the retrievers answers as well as the output of the whole RAG pipeline.

Benchmark-Based Evaluation

For more comprehensive evaluation, standardized benchmark-systems like RAGChecker offer systematic frameworks for assessing RAG systems across multiple dimensions based on ground-truth-datasets. RAGChecker evaluates:

  1. Retriever precision and recall: Quality of document retrieval
  2. Overall accuracy: Correctness of final answers
  3. Hallucination detection: Identification of generated content not supported by retrieved documents
  4. Missing information: Detection of incomplete answers

These benchmarks use curated datasets with ground-truth answers, allowing you to compare your system’s performance against baselines.

Choosing Between Evaluation Approaches

Both DeepEval- and RAGChecker-like evaluation has distinct advantages and limitations:

A system like RAGChecker provides solid metric calculation based on ground truth data, offering objective and reproducible scores. However, benchmark datasets might not be comparable to your specific task or domain, limiting their practical applicability to real-world use cases.

On the other hand, using a strategy similar to that implemented in DeepEval, does not require pre-existing ground truth and can evaluate systems on any domain or dataset, making it highly flexible. However, it relies on another LLM for evaluation, which introduces two key concerns: (1) the evaluating LLM itself can hallucinate, potentially providing unreliable assessments, and (2) extensive evaluation using LLM-as-judge can be costly, especially when evaluating large numbers of queries or iterating frequently during development.
